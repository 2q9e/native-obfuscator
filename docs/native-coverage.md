# JNI coverage and verification

Native conversion checks operand types before emitting JNI calls. Frame analysis preserves exact array and object descriptors and checks assignments it can prove from bytecode and descriptors. External call bridges also use superclass and interface edges from unversioned class headers in the input JAR. When that proof widens a reference argument, the bridge keeps the operand's original type and executes the symbolic invocation in the JVM. For types outside the input JAR, repeat `--hierarchy-jar PATH` with the runtime dependency JARs in the bytecode's namespace. Use the same options for `protect`, `harden`, `verify`, and `apply`. JSON configurations accept a `hierarchyJar` array of paths. Input headers take precedence. Conflicting dependency definitions and multi-release variants supply no superclass or interface edges. The protected JAR uses the application's existing runtime classpath. A method stays in Java under `--unsupported retain` when the translator cannot prove a required assignment. The default policy fails the build. Diagnostics identify the instruction and reason.

The verified additions are:

| Operation | Accepted slice | Semantics checked |
| --- | --- | --- |
| Array length | Proven primitive/reference array descriptors | Null checks and length |
| Array loads and stores | All eight primitive element types, reference elements, and arrays containing arrays, with an exact descriptor | Signed byte/short extension, unsigned char extension, boolean low-bit stores, null before bounds before reference-store compatibility, category-2 values |
| Object allocation | Contiguous construction with local loads and primitive or null constants | New identity, constructor arguments, lazy initialization, and propagation of constructor failures |
| Array allocation | Primitive, reference, and multi-dimensional allocations | Component type, zero initialization, negative and zero dimensions, class resolution failures, and repeated allocation in loops |
| Fields | Static and instance fields of primitive or reference type declared by the translated method's class | Null receivers, narrow values, reference identity, final-write rejection, descriptors and staticness |
| Direct calls | Static calls, virtual dispatch, and private calls within the translated method's class | Null receivers, virtual overrides, private dispatch on subclass receivers, primitive ABI categories, reference arguments and results used within the method, exception propagation |
| Cross-class static calls | JVM linkage bridges for external static class and interface methods | Lazy initialization of the resolved declaring class, nestmate access, missing methods, exception propagation, full JVM int-stack arguments |
| Cross-class instance calls | External virtual and interface dispatch with a proven receiver type | Overrides, interface defaults, null receivers, and resolution errors before null checks |
| Super calls | `invokespecial` to a proven superclass or direct superinterface, executed in a caller-class bridge | Superclass lookup through an intermediate override, explicit interface-default dispatch, null receivers, linkage errors, and caught exception identity |
| Cross-class fields | Static and instance field reads and writes in JVM linkage bridges | Lazy initialization, nestmate access, reference identity, volatile JVM operations, and resolution errors before null checks |
| Reference returns | Proven object and array return assignments | Receiver and array identity, nulls, covariant arrays, array and call exceptions, and generic bridge dispatch |
| Casts and type tests | JVM `CHECKCAST` and `INSTANCEOF` bridges | Object and array identity, null, cast and linkage errors, and casts in loops without JNI reference accumulation |
| Dynamic string concatenation | The standard `StringConcatFactory` bootstraps with string or primitive constants | Recipe ordering, null and numeric operands, and reference results from repeated concatenation |
| Dynamic lambda factories | Standard `LambdaMetafactory.metafactory` and serializable `altMetafactory` sites with no extra marker interfaces or bridge signatures | Java and Kotlin captures, bound and constructor references, per-site linkage, bootstrap failures, functions carried across loops, and matching serialized bytes and restored behavior for Java lambdas |
| Memory ordering | Volatile field reads and writes through JVM bridges, plus synchronized method modifiers preserved at JNI entry | Cross-thread publication, monitor ownership, and concurrent increments |
| Explicit throws | JVM `ATHROW` bridge with a proven throwable reference | Original throwable identity, null-to-`NullPointerException` behavior, and local catch or propagation |
| Exception handlers | Forward and backward paths, including cycles that retain the caught throwable | JVM table order, nested handlers, exceptional finally execution, throwable identity, linkage failures, and exception-driven loops |
| JNI references in loops | Verified local and stack slots at normal and exceptional backward targets | Loop-carried identity, aliases, switch backedges, allocation, and object-returning calls that throw within loops |
| Reference equality | Existing JNI identity comparison | Distinct JNI handles referring to the same Java object compare equal |

Every JNI lookup or potentially throwing operation checks for a pending exception before execution continues. Static JNI entries use the class handle supplied by the JVM for declaring-class lookups. Instance entries resolve the declaring class on first use and keep its local handle for the invocation. Acyclic methods keep reference results for the invocation. In cyclic methods, backward targets reclaim owned JNI handles outside the verifier's reference slots. An object-returning JNI operation in a protected range uses a temporary local frame so a failed call releases its temporary references before handler execution. Outside a protected range, it records the result directly after checking for a pending exception, since a failure exits the invocation and releases its JNI references. Exception routing also reserves capacity for each protected operation that can produce a caught throwable. A JVM bridge applies the original exception table order. Native handler code resumes with the original throwable as its sole stack operand. If the handler immediately pops it or stores it into a local slot the method never loads as a reference, the native code releases the caught JNI handle before entering the handler. For methods that may need more than JNI's guaranteed 16 local slots, it reserves capacity with `EnsureLocalCapacity` and propagates allocation failure. The bound includes the handles that can survive cleanup and the reference producers that can execute before the next cleanup. A differential fixture performs 64 reference loads in one invocation. Primitive array loops remain supported. Category-aware stack duplication covers long and double array and field compound assignments. POP, POP2, and SWAP check operand categories explicitly.

The unsupported policy applies to unproven super dispatch, construction with effectful argument evaluation, explicit monitors, and dynamic calls outside the supported bootstrap forms. Narrow JNI call arguments must be proven to fit their descriptors. An ASM fixture passes 257 to a Java method with a byte parameter and observes 257 in its Java body. The translator retains the caller to preserve that result. The native entry ABI assumes ordinary descriptor-range arguments from its Java callers.

External calls, external and volatile fields, and type checks execute their original JVM instruction in a private synthetic method in the caller class. The bridge remains visible in bytecode and adds a Java stack frame. JNI passes narrow primitive arguments as full stack integers to these bridges.

A wrapper `valueOf` followed immediately by an erased instance call, a return cast, and an unbox can share one bridge. The JVM executes the four instructions in their original order. Labelled instruction boundaries keep the calls in separate bridges. Use the same compiler version for staging and verification because the verifier reconstructs the exact bridge bytecode.

Exception tests compare exception classes and observable state, including side effects after a failed JNI operation. Bounds errors include the index and length. Helpful null-pointer and array-store messages and JVM stack frames can differ after conversion.

Run the standalone differential suite against an installed distribution:

```text
python src/test/native-coverage/verify.py build/install/native-obfuscator --work build/native-coverage --zig /path/to/zig --target all
```

Additional native build flags, including `--profile`, `--seed`, and the matching LLVM tool paths, are forwarded to `protect`. The GitHub Actions runtime matrix executes the cross-built coverage fixture on Windows and Ubuntu x64 and ARM64, including a staged build whose hierarchy proof uses a separate runtime dependency. The optional work directory preserves the original/protected JARs, Java outputs, compiler diagnostics, actual native declarations, operand-check output, and a JSON result. Keep these local artifacts outside release archives.

On November 21, 2026, the suite passed using JDK 25.0.5 and Java 21 classfiles, Zig 0.15.2, and LLVM 23.1.6. Both the compatibility C path and balanced LLVM path with seed 42 converted 32 methods. Each build matched 126 result, exception, and state lines, including 34 array-bounds, 17 null-pointer, one array-store, and one arithmetic exception, as well as a checksum over 20,000 randomized native calls. Eight malformed operand, stack-category, field, and call cases were rejected before compilation. The suite checks actual native declarations and selection diagnostics and enables `-Xverify:all` and `-Xcheck:jni`. The compatibility run also exercised a Turkish JVM locale.

All four supported targets were built in both runs. Windows x64 executed. Linux x64, Linux ARM64, and Windows ARM64 were cross-built. A separate Windows x64 compatibility run matched all 126 outcomes on JDK 21.0.12. The balanced pass transformed eight sites across six of the 32 methods on each target. The other 26 methods reported zero sites. The local Windows opt driver linked the checked-in pass statically because the installed LLVM distribution lacks dynamic plugin support. Windows dynamic plugin loading remains unverified.
