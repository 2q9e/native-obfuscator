# Local verification

These checks ran on Fedora Asahi ARM64 with Temurin 25.0.5, Zulu 21.0.13.1,
Zig 0.15.2, and Fedora LLVM 23.1.4. Java classfile and JNI verification
were enabled in the differential runs.

| Check | Result |
| --- | --- |
| Gradle application distribution | Built with Gradle 9.3.1 |
| Java 21 and 25 differential fixture | Both versions matched digest `55cfd63f18498e67`. Eighteen methods became native. Lambda, array access, and explicit exception throw kept the Java body. |
| Generated bytecode differential | At each of two program seeds, 60 methods and 60,000 calls matched on both Java 21 and 25. Duplicate native builds matched byte for byte. |
| Kotlin 2.2.21 | Both JDKs verified native instance and top-level methods, retained Kotlin lambda and callable reference behavior, and preserved Kotlin metadata and reflection. |
| Fabric 1.21.11 | Production Loader/Mixin discovered the protected JAR in Minecraft's `--help` launch. A separate initializer run on both JDKs invoked the native kernel and verified the Mixin accessor and access widener. Full world startup and shutdown remain unverified. |
| Modern classfiles | Java 21 and 25 executed a retained `ConstantDynamic` bootstrap once, converted a method with supplementary Unicode in its name and descriptor, and preserved record metadata and generic bridge dispatch. |
| Tamper and archive checks | Native library checksum mismatch, duplicate archive entries, traversal paths, signing files, and malformed classfiles were rejected. Strict-mode failure preserved an existing output file. |
| LLVM arithmetic pass | Host differential test passed 100,324 input pairs per build and checked seed reproducibility, input validation, prefix and budget filtering, and instruction survival. |
| LLVM control-flow diversification | Native differential passed with 100,324 pairs per build. Final linked Linux ARM64 code retained the conditional branch. Linux and Windows ELF/COFF inspection showed the branch on both architectures. |
| LLVM all-target packaging and host execution | A single JAR packaged all four libraries. The Linux ARM64 library ran with JNI checks enabled and matched the JVM digest. |
| LLVM Linux x64 and both Windows targets | Cross-compiled. Object disassembly tests confirm arithmetic transformation survives code generation on all four architectures and formats. |

A separate ARM64 build with a 0% budget rejected the JAR even though the two
shared objects had identical total file sizes due to section alignment.

One Fedora ARM64 run of `benchmarks/run.sh` used nine measured samples after
five warmups. Values are median nanoseconds per call. The original Java JIT
can inline the boundary workload, which accounts for much of the difference.

| Workload | Java | JNI only | Balanced LLVM |
| --- | ---: | ---: | ---: |
| Boundary | 0.943 | 3.018 | 3.019 |
| Arithmetic | 38.520 | 37.617 | 41.894 |

The three runs matched both workload checksums. The balanced arithmetic
workload took 8.76% longer than Java in this run. These timings are from a
single host and measure a small synthetic workload.

See the [LLVM pass test instructions](../llvm/README.md) for disassembly and
reproducibility checks. The workflow runs target-native checks separately from
cross-compilation.

## Windows x64 verification on November 21, 2026

Windows x64 execution passed with Temurin 21.0.12 and 25.0.5 and Zig 0.15.2. The arithmetic, generated bytecode, and modern classfile fixtures also ran with Java 25 classfiles under JDK 25. Arithmetic still matched digest `55cfd63f18498e67`, with 19 native methods after the new array coverage. Four JDK 25 generated-kernel runs matched 60,000 calls each and reproduced their compiled JARs byte for byte. Kotlin 2.2.21 passed on both JDKs. Its lambda implementation now converts, while the dynamic lambda factory and callable-reference allocation stay Java. The Fabric 1.21.11 smoke test exercised production mod discovery and matched the native kernel, Mixin accessor, and access-widener results on both JDKs. It ran through help and mod initialization.

Archive rejection, registration and library tampering, and strict output preservation passed. A maximum LLVM build with 12 padding classes grew Windows x64 executable code from 11,670 to 13,094 bytes. A 0% growth budget rejected that build and preserved the existing destination. LLVM arithmetic and branch diversification passed local execution, reproducibility, zero-site reporting, and object-code checks for all four targets. Windows pass tests used a locally linked static opt driver built from the project pass and LLVM 23.1.6. Dynamic plugin loading on Windows was outside that test.

The new JNI differential suite reports compared values and exceptions, and the padding report records timings, archive growth, final class distributions, false positives, and misses. [JNI coverage](native-coverage.md) · [Padding measurements](padding-heuristics.md)
